# Go2 行走：从理解控制到强化学习训练

这是一份待逐步完成的学习路线，文中提到的新 Python 文件目前均为计划，并不表示已经实现。

目标：能够解释 Go2 行走代码中的数据流，自己实现最小环境，并训练出平地速度跟踪策略。先做仿真，真机部署留作后续独立阶段。

## 1. 路线选择：先 SB3 理解闭环，再用 mjlab 加速

针对“强化学习新手，希望逐步理解每一部分”的目标，建议采用：

```text
已有的原生 MuJoCo + PD 控制
        ↓
自己编写一个 Gymnasium 环境
        ↓
用 SB3 的 PPO 完成最小训练、保存、回放
        ↓
把已经理解的环境逻辑对应到 mjlab
        ↓
用 mjlab + RSL-RL 进行 GPU 并行行走训练
```

SB3 阶段的目标是把环境和训练闭环看清楚。完成一次可解释的最小训练后，就可以迁移，不要求先在 CPU 上把完整行走任务调到满意。

| 比较 | 原生 MuJoCo + Gymnasium + SB3 | mjlab + RSL-RL |
| --- | --- | --- |
| 代码阅读 | 可以从一个 `step()` 顺着读完 | 要追踪配置、管理器和具体函数 |
| 动手学习 | 自己写动作、观测、奖励和重置，关系直观 | 用模块组织同样的逻辑，需要理解框架调用顺序 |
| 调试 | 单环境容易逐行打印、断点检查 | 需要逐步掌握批量张量和按环境重置 |
| 常见计算方式 | CPU 运行 MuJoCo；网络可在 CPU/GPU 上计算 | GPU 并行物理仿真，并进行网络计算 |
| 官方 Go2 参考 | 需要自己对照和移植 | 可对照宇树 `unitree_rl_mjlab` |
| 主要代价 | 后续并行和工程功能需要自己组织 | 初期框架概念多，依赖版本需要配套 |

两条路线都可以使用 PPO。框架不会代替动作、奖励、坐标系等设计，也不会自动保证策略学会行走。初学用 SB3 更容易看清环境调用关系，但 PPO 内部在两条路线中都需要主动阅读。

### GPU 应该怎样使用

- 原生 MuJoCo 环境中，SB3 的 `device="cuda"` 只改变网络计算位置，不会把物理仿真自动移到 GPU。
- 小型数值观测网络使用 SB3 PPO 时，CPU 可能更合适，先测量采样速度再决定。
- mjlab 使用 MuJoCo Warp 做 GPU 并行仿真，官方训练要求 NVIDIA GPU。
- 调试从 1 个环境开始；训练逐步增加并行数，以显存占用和实际吞吐量为依据。
- 正式搭建前记录显卡型号、显存、驱动、Python 和依赖版本。SB3 与 mjlab 建议使用独立虚拟环境。

## 2. 先理解整条数据流

```text
观测 obs + 速度指令 command
          ↓
策略网络 actor
          ↓
12 维动作 action
          ↓
目标关节角度 q_target
          ↓
PD 控制器计算力矩 torque
          ↓
MuJoCo 推进若干物理步
          ↓
新观测、奖励、是否结束
          ↓
收集一批交互数据 → PPO 更新网络 → 继续采样
```

需要分清三件事：

1. PD 控制让关节跟随目标角度，它本身不会学习。
2. 策略根据观测输出动作；训练时通常带探索，评估时通常使用确定性动作。
3. PPO 根据交互数据更新策略；奖励参与训练，部署执行策略时通常不需要计算奖励。

## 3. 分步学习清单

每一步都遵循：先读原理 → 写少量代码 → 查看数值与画面 → 记录结论。每次只改变一类因素。

### 第 0 步：确认已有基础

参考现有文件：

- [机器人信息](../test/01_robot_info.py)
- [模型查看](../test/02_viewer.py)
- [世界坐标读取](../test/04_body_xpos.py)
- [PD 保持站姿](../test/06_pd_hold.py)
- [当前使用的场景模型](../xmls/scene_go2.xml)

任务：

- [ ] 分清 `model`（模型参数）和 `data`（当前仿真状态）。
- [ ] 分清 `qpos`、`qvel`、`ctrl`，理解浮动基座为什么使 `nq` 和 `nv` 不同。
- [ ] 打印执行器名称、对应关节、位置索引、速度索引和力矩范围。
- [ ] 从 `home` 初始化，运行 PD 站立，记录高度、关节误差和力矩。

注意：当前模型执行器顺序与 XML 中关节出现顺序不同。沿用 `06_pd_hold.py` 的执行器到关节映射，不要直接假设数组切片顺序一致。

验收：能解释为什么零力矩会倒下，以及 PD 保持站姿为什么还不等于强化学习。

### 第 1 步：让动作通过 PD 控制关节

计划文件：`01_action_control.py`。

原理：策略先输出目标角度偏移，由 PD 产生力矩。

```text
action ∈ [-1, 1]^12
q_target = q_default + action_scale × action
torque = Kp × (q_target - q) - Kd × dq
```

任务：

- [ ] 从现有 PD 脚本提取默认姿态与关节索引。
- [ ] 输入零动作，确认目标角度等于默认姿态。
- [ ] 只给一个关节小幅动作，查看实际运动方向。
- [ ] 给一个关节小幅正弦目标，观察目标与实际角度的差异。
- [ ] 对目标角度和力矩做合理限制，并记录限幅前后的值。

`action_scale` 的单位是弧度。现有 PD 增益是起点，需要观察误差、振荡和力矩饱和情况，再决定是否调整。

验收：能指出动作的某一维控制哪条腿的哪个关节，并解释动作值如何变成力矩。

### 第 2 步：区分物理频率和策略频率

计划文件：在第 1 步基础上增加控制步函数，后续放入 `go2_env.py`。

原理：策略不必在每个物理步重新决策。

```text
physics_dt = model.opt.timestep
control_dt = physics_dt × decimation
```

例如物理步长为 0.002 秒、`decimation=10` 时，一个动作持续 0.02 秒，策略频率为 50 Hz。这只是示例，实际读取模型参数后再确定。

任务：

- [ ] 一次控制步生成目标角度，并在多个物理步中保持目标。
- [ ] 每个物理步根据最新的角度和速度重新计算 PD 力矩。
- [ ] 打印控制步数、物理步数和仿真时间，检查三者关系。
- [ ] 只在观看时进行画面刷新与限速；训练循环中不使用 `sleep()`。

验收：能解释“保持动作”和“保持力矩”的区别，以及改变控制周期为什么会影响行为。

### 第 3 步：定义机器人能看到什么

计划文件：`02_observation.py`，确认后并入 `go2_env.py`。

先做一个明确的教学版观测，例如：

| 内容 | 维度 | 含义 |
| --- | --- | --- |
| 机身线速度 | 3 | 机身坐标系中的前后、左右、上下速度 |
| 机身角速度 | 3 | 绕机身三个轴的转动速度 |
| 重力方向 | 3 | 世界向下单位向量在机身坐标系中的表达 |
| 速度指令 | 3 | 期望前进速度、横向速度、偏航角速度 |
| 关节角度偏差 | 12 | 相对默认站姿的关节角度 |
| 关节速度 | 12 | 与动作顺序一致的关节角速度 |
| 上一步动作 | 12 | 上一个控制周期执行的动作 |
| 合计 | 48 | 本路线的教学设计，并非官方任务的固定定义 |

任务：

- [ ] 为每组数据注明单位、坐标系和顺序，使用一致的 `float32` 数据类型。
- [ ] 用明确的 MuJoCo API 或传感器获取速度，核对坐标系，避免把原始数组切片当成机身速度。
- [ ] 检查 MuJoCo 四元数顺序，验证世界坐标到机身坐标的旋转方向。
- [ ] 水平站立时，验证重力方向接近 `[0, 0, -1]`；倾斜机身后检查变化。
- [ ] 明确 `step()` 返回的新观测中，“上一步动作”就是刚刚执行的动作；重置时清零。
- [ ] 检查所有数值有限，记录各分量的大致量级，再选择固定缩放或运行统计归一化。

仿真可以直接提供真实线速度，真机未必能直接获得。先用它学习，迁移真机前再考虑状态估计、历史观测或 actor/critic 使用不同观测。

验收：不看代码也能说清 48 个数分别来自哪里，以及为什么需要它们。

### 第 4 步：写一个最小 Gymnasium 环境

计划文件：`go2_env.py`、`03_check_env.py`。

接口：

```python
obs, info = env.reset(seed=0)
obs, reward, terminated, truncated, info = env.step(action)
```

任务：

- [ ] 定义动作空间、观测空间和模型路径。
- [ ] `reset()` 恢复 home、清理控制量、动作历史和计步器，更新派生状态。
- [ ] 随机化通过环境自身的随机数生成器进行，使相同种子可复现。
- [ ] `step()` 完成动作处理、物理推进、奖励、结束判断和新观测。
- [ ] 跌倒作为任务终止 `terminated`；外部时间上限作为 `truncated`。
- [ ] 先用机身倾斜与高度判断跌倒；阈值依据实际站姿确定。
- [ ] 每个物理子步检查明显跌倒或数值异常，避免继续推进无效状态。
- [ ] 分别运行零动作、小动作和随机动作；随机动作跌倒是正常现象。
- [ ] 使用 SB3 `check_env` 检查接口，再人工检查物理含义。

SB3 的 `VecEnv` 与原始 Gymnasium 接口不同：前者 `reset()` 返回观测，`step()` 返回四项，并自动重置结束的环境。接入包装器时阅读官方接口说明，不要混用。

验收：多次重置后没有上一回合的历史残留；时间上限与跌倒能区分；接口检查通过。

### 第 5 步：先设计可解释的站立奖励

计划位置：`go2_env.py` 中独立的奖励函数。

任务：

- [ ] 奖励直立和接近合理站立高度。
- [ ] 惩罚不需要的机身运动、过大力矩和动作突变。
- [ ] 在 `info` 中分别记录原始奖励项与加权奖励项。
- [ ] 用站立、倾斜、低矮倒地等状态检查每项数值。
- [ ] 明确每项是按控制步计算，还是按时间积分；修改控制周期时检查奖励尺度。
- [ ] 分析提前终止是否让策略通过快速跌倒逃避持续惩罚。

不要一开始照抄一长串奖励权重。先能解释每项鼓励什么行为，再决定加入哪项。

验收：合理站立的表现优于明显倒地；能解释奖励总分是怎样组成的。

### 第 6 步：用 SB3 PPO 完成最小学习闭环

计划文件：`train_sb3.py`、`play_sb3.py`。

任务：

- [ ] 用小型 MLP 和现成 PPO 开始，不先自己实现 PPO。
- [ ] 完成短训练，确认数据采集、参数更新、日志和模型保存都正常。
- [ ] 单独运行回放脚本，加载模型并使用确定性动作评估。
- [ ] 若使用 `VecNormalize`，同时保存统计量；评估加载同一份统计量并停止更新。
- [ ] 与零动作 PD 基线比较回合时长、姿态、关节偏差和力矩。
- [ ] 在小幅初始姿态扰动下重复评估，确认结果不是只来自固定初态。
- [ ] 保存依赖版本、种子、动作缩放、增益、控制周期、观测顺序和奖励权重。

固定 home 下，零动作 PD 本来就可能站得很好。训练程序跑通不等于策略学到了更好的控制，需要基线和扰动评估支持结论。

验收：能够训练、保存、重新加载、评估，并解释结果。无需先得到完美站立或行走策略；如果采样很慢，可完成短训练检查后转入 mjlab。

### 第 7 步：顺着一次训练理解 PPO

计划文件：`notes/ppo.md`，先写自己的解释和小例子。

按以下顺序学习：

1. **Actor**：根据观测输出动作分布，训练时怎样探索。
2. **Critic**：估计从当前状态开始的未来折扣回报。
3. **Rollout**：收集哪些状态、动作、奖励、结束标记和概率信息。
4. **Return / Advantage**：实际回报与预期相比怎样；GAE 如何利用奖励和价值估计。
5. **PPO 更新**：新旧动作概率之比、裁剪目标，以及为什么限制更新幅度。
6. **训练参数**：`n_steps`、环境数、`batch_size`、`n_epochs` 各改变什么。

任务：

- [ ] 画出一次“采样 → 估计回报/优势 → 多轮小批量更新”的过程。
- [ ] 阅读日志中的回合长度、回报、价值损失、熵和近似 KL，理解各自用途。
- [ ] 分清任务终止与超时截断对价值自举的影响。
- [ ] 能解释为什么回报上涨并不一定意味着机器人走得更好。

验收：能用自己的话解释策略为什么会改变，而不仅是会调用 `learn()`。

### 第 8 步：把已理解的逻辑对应到 mjlab

计划目录：`mjlab_go2/`。先独立配置依赖，并固定与官方参考项目兼容的版本。

| 已实现的逻辑 | 在 mjlab 中查找的对应位置 |
| --- | --- |
| 机器人模型、地面、初始姿态 | Entity / Scene 配置 |
| 动作缩放、默认姿态、执行器控制 | Actions / Actuators |
| 观测拼接、缩放与噪声 | Observations |
| 期望速度 | Commands |
| 奖励计算 | Rewards |
| 跌倒与超时判断 | Terminations |
| 重置、初态扰动、参数随机化 | Events / Domain Randomization |
| 采样与 PPO 更新 | RSL-RL 接口和训练器 |

任务：

- [ ] 找到上述配置实际调用的函数，追踪一次动作执行和一次重置。
- [ ] 从单环境开始，检查零动作、小动作、观测和奖励。
- [ ] 核对模型参数、关节顺序、增益、控制周期和四元数约定。
- [ ] 扩展到少量环境，检查动作 `[N, 12]`、观测 `[N, obs_dim]` 等张量形状。
- [ ] 只重置其中一个环境，确认其他环境的状态和历史不受影响。
- [ ] 逐步增加并行数，记录采样速度、显存与训练更新耗时。

迁移的是环境设计和理解。SB3 模型文件、归一化统计量不能直接当作 RSL-RL 检查点加载；教学阶段优先重新训练。CPU MuJoCo 与 Warp 的轨迹也不要求逐位相同。

验收：每个重要配置都能追到执行函数，并能说明它对应自己之前写过的哪段逻辑。

### 第 9 步：用 mjlab 学习平地向前走

先固定一个较小的正向速度目标，例如 0.2 m/s；这是教学起点，需要根据实际表现调整。

任务：

- [ ] 将速度指令放入观测，奖励机身速度跟踪目标。
- [ ] 保留直立、适当高度、力矩和动作平滑约束，避免过强站姿约束阻止迈步。
- [ ] 不强制必须先模仿某种步态；先观察策略自然学出的行为。
- [ ] 记录速度误差、跌倒比例、回合时长和每项奖励。
- [ ] 查看视频，排查滑行、倒地挪动、持续跳跃等获得奖励的取巧行为。
- [ ] 达到稳定前进后，加入零速度，再逐步增加不同前进速度。
- [ ] 最后扩展横向速度和转弯，明确指令与测量速度采用相同坐标系。

验收：在事先设定的多次评估中，持续保持直立并跟踪目标速度。用实际速度误差和跌倒次数说明表现，不只展示一次成功视频。

### 第 10 步：提高稳定性，再考虑真机

任务：

- [ ] 逐项加入初始状态变化、摩擦变化和轻微外力扰动。
- [ ] 再研究质量变化、执行器响应、控制延迟、观测噪声等随机化。
- [ ] 每次加入一类变化，比较相同评估条件下的表现。
- [ ] 学习课程设计，逐步增加任务难度。
- [ ] 阅读官方推理与部署代码，核对动作、观测、归一化和频率约定。
- [ ] 在独立的仿真推理程序中验证导出策略，再单独制定真机验证步骤。

验收：能够说明策略适用的速度与扰动范围，也能指出尚未验证的条件。仿真成功不等于真机部署完成。
